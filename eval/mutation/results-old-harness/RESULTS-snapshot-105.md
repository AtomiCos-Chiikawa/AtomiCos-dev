# 변이 평가 중간 결과 (2026-11-19 22시 41분 기준, 105개)

> 이 문서는 실행 중인 변이 평가를 **22시 41분에 끊어서 본 중간 결과**다. 이때까지 105개 변이가 끝났다(실행 완료 97개 + 빌드 실패로 제외 8개). 실행은 계속되고 있으므로 최종 숫자는 바뀔 수 있다.
> 숫자는 모두 자동 집계 [`results/report-snapshot.md`](results/report-snapshot.md)에서 가져왔다. 평가 방법의 사전 정의는 [`README.md`](README.md)에 있다.

## 한눈에 보기

| 방법 | 잡은 변이 (실행 완료 97개 기준) |
|---|---|
| **AtomiCos 판정기** | 12/97 = **12%** (95% 신뢰 구간 7–20%) |
| **기존 테스트** (업스트림 통합 테스트 8묶음) | 35/97 = **36%** (27–46%) |
| **거래 전후 총발행량 비교** (A1) | 0/97 = **0%** (0–4%) |
| 판정기 또는 기존 테스트 | 37/97 = 38% (29–48%) |

- 판정기만 단독으로 놓고 보면 **기존 테스트보다 적게 잡는다.**
- 그 대신 **기존 테스트가 통과시킨 버그를 판정기만 잡은 경우가 2개** 있다(A01, C028). 둘 다 다시 돌려서 같은 결과가 나오는 것을 확인했다.
- **거래 전후 비교는 하나도 잡지 못했다.** 거래가 끝난 뒤 총량만 비교해서는 이런 버그가 보이지 않는다.
- 판정기가 잡은 12개 중 8개는 **precompile 경계 관찰(O2)을 빼면 못 잡는다.** 탐지의 중심은 경계 관찰이다.
- 97개 중 **62개(64%)는 판정기도 기존 테스트도 잡지 못했다.** 정상 테스트 입력으로는 버그가 실제로 드러나지 않는 경우가 많다는 뜻이다.

## 1. 무엇을 쟀나

AtomiCos 판정기가 **처음 보는 버그를 얼마나 잡는지** 쟀다.

판정 규칙은 GHSA 세 사례(mjfq·8pfh·7g4w)를 보고 설계했다. 그래서 그 세 사례를 잡았다는 7단계 결과는 성능 근거가 될 수 없다. 이미 답을 보고 만든 규칙이기 때문이다. 이 평가에서는 cosmos/evm **v0.7.4** 코드에 버그를 **기계적으로** 심은 변형 버전(변이)을 많이 만들고, 각 변이를 세 가지 방법이 잡는지 비교했다.

세 방법은 모두 **같은 실행, 같은 입력**을 본다. 입력은 cosmos/evm에 원래 들어 있는 정상 테스트다. 따라서 이 평가가 재는 것은 **판정기 자체의 성능**이다. 버그를 일부러 터뜨리는 입력을 만드는 입력 생성기는 아직 없다(8단계 이후 과제).

## 2. 비교한 세 방법

### 2.1 AtomiCos 판정기

v0.7.4에 관찰 훅(하네스)을 붙여 실행하면, precompile이 상태를 바꾸는 순간들이 기록(trace)으로 남는다. 판정기는 이 기록을 읽고 규칙 위반을 찾는다.

| 관찰 지점 | 보는 것 |
|---|---|
| O2 | precompile에 들어갈 때·나올 때의 EVM 잔고와 Cosmos(bank) 잔고 |
| O4 | 잔고 변경 |
| O5 | 스냅샷과 되돌림 |
| O6 | 커밋 |

| 규칙 | 내용 |
|---|---|
| R1-S / R1-E | 되돌린 호출이 남긴 상태 변경·이벤트가 최종 커밋에 남으면 안 된다 |
| R2-A / R2-W | 잔고 산술이 넘치거나 모자라면 안 되고, StateDB 잔고와 bank 잔고가 커밋 때 맞아야 한다 |
| R3-D/U/C | staking·distribution 기능 단위 일관성 (위임, 위임 해제, 보상 인출) |
| A1 (보조) | 총발행량이 거래 전후로 바뀌지 않아야 한다 |

판정기는 **정답 값을 모른다.** "이 거래 뒤 잔고가 정확히 얼마여야 한다"를 알지 못하고, 어느 거래에나 통하는 일반 규칙만 본다.

### 2.2 기존 테스트 (업스트림 통합 테스트 8묶음)

cosmos/evm 저장소에 원래 들어 있는 **precompile 통합 테스트**다. 개발팀이 직접 작성했고, 실제 체인과 같은 구성의 테스트 체인을 프로세스 안에 띄운 뒤 precompile을 호출한다. Ginkgo 테스트 프레임워크로 작성돼 있다. 테스트 코드는 `tests/integration/precompiles/<이름>/`에 있고, `evmd/tests/integration/precompiles/<이름>/`에서 실행한다.

각 테스트는 precompile을 **EOA가 직접 호출**하거나 **Solidity 컨트랙트를 거쳐 호출**한다. 그리고 시나리오마다 정답을 알고 확인한다.
- 호출이 성공해야 하는지, 실패해야 하는지
- 반환값
- 호출 뒤 잔고와 위임 상태
- 발생한 이벤트

| 묶음 | 실행하는 테스트 함수 | 테스트 블록(`It`) 수 | 대조군 실행 시간 | 주로 다루는 것 |
|---|---|---|---|---|
| staking | `TestStakingPrecompileIntegrationTestSuite` | 83 (실행 시 92개 spec) | 113초 | 위임·위임 해제·재위임, 컨트랙트 경유 호출, 네이티브 코인 전송과 함께 호출, 호출 전 StateDB 변경, 한 함수 안의 여러 상태 변경, 특수 call opcode, 베스팅 계정 |
| distribution | `TestDistributionPrecompileIntegrationTestSuite` | 64 | 61초 | 보상 인출, 인출 주소 설정, 커미션, 커뮤니티 풀, 컨트랙트가 위임자인 경우 |
| bank | `TestBankPrecompileIntegrationTestSuite` | 19 | 23초 | 잔고·총발행량 조회 (직접 호출, 컨트랙트 경유) |
| erc20 | `TestErc20IntegrationTestSuite` | 16 (표 형태 테스트가 많음) | 200초 | 전송·승인·메타데이터, 컨트랙트 간 호출, 마이그레이션 흐름 |
| werc20 | `TestWERC20PrecompileIntegrationTestSuite` | 25 | 37초 | 래핑 코인 입금·출금, 되돌리는 컨트랙트 호출 |
| gov | `TestGovPrecompileIntegrationTestSuite` | 32 | 39초 | 제안·예치·투표·취소, 컨트랙트 경유, 환불 보안 문제 |
| slashing | `TestStakingPrecompileIntegrationTestSuite`(slashing 패키지 안의 같은 이름 함수) | 1 | 14초 | 컨트랙트에서 unjail 호출 |
| ics20 | `TestICS20PrecompileIntegrationTestSuite` | 6 | 26초 | 컨트랙트에서 IBC 전송 호출 |

`It` 수는 v0.7.4 소스에서 센 값이다. 표 형태 테스트는 한 `It`가 여러 spec으로 늘어나므로 실제 실행 수는 더 많다.

**기존 테스트가 "잡았다"의 정의:** 변이를 넣은 코드에서 해당 묶음이 다음 중 하나로 끝나면 잡은 것으로 센다(일반적인 변이 테스트 관례).

| 판정 | 뜻 |
|---|---|
| `FAIL` | 테스트 확인문(assertion) 하나 이상이 실패 |
| `PANIC` | 테스트가 panic으로 중단 |
| `TIMEOUT` | 20분 안에 끝나지 않음 |
| `MEMOUT` | 메모리를 3GB 넘게 써서 자동 종료 (대조군 최대는 erc20 약 2.1GB) |

이번 중간 결과에서 기존 테스트가 잡은 방식은 `FAIL` 35건, `MEMOUT` 2건이다(한 변이가 여러 묶음에서 잡히면 각각 셈).

### 2.3 거래 전후 총발행량 비교 (A1)

가장 단순한 기준선이다. 같은 기록에서 **최상위 StateDB를 처음 관찰했을 때와 커밋 직후의 총발행량**을 비교해, 달라졌으면 잡은 것으로 센다. "거래 전후만 비교하면 되지 않느냐"는 질문에 답하려고 넣었다.

### 3.3 도달 여부로 거르기
깨끗한 v0.7.4에서 8묶음을 커버리지 측정과 함께 한 번 돌렸다. 변이가 바꾼 줄을 **어느 묶음도 실행하지 않으면 "도달 못 함"**으로 분류하고 돌리지 않는다. 돌려 봐야 원본과 결과가 같을 수밖에 없기 때문이다. 줄을 실행한 묶음만 그 변이의 입력으로 쓴다.

| 묶음 | 연산자 | 생성 | 도달 |
|---|---|---|---|
| A | FIX-REVERT | 11 | 10 |
| B1 | DEL | 88 | 59 |
| B1 | ERR | 111 | 19 |
| B1 | GUARD | 114 | 91 |
| B1 | LOCK | 3 | 3 |
| B1 | SWAP | 11 | 9 |
| B2 | DEL | 21 | 19 |
| B2 | ERR | 16 | 14 |
| B2 | GUARD | 23 | 22 |
| **합계** | | **398** | **246** |

`ERR`은 111개 중 19개만 도달했다. 정상 테스트가 오류 경로를 거의 지나가지 않기 때문이다. 이 결과 자체가 입력 생성기가 필요한 이유 중 하나다.

8pfh 계열 A02·A03은 설계 확인용 사례라 평가에서 뺐다. 따라서 실행 대상은 **244개**다.

## 4. 실행 방법

1. **대조군:** 변이 없는 코드에 하네스를 붙여 8묶음을 돌렸다. 결과는 **테스트 모두 PASS, 판정기 위반 0건, A1 0건**이다. 판정기가 정상 코드에서 잘못 울리지 않는다는 기준이다.
2. **변이마다:** 깨끗한 코드 → 변이 패치 적용 → 하네스 삽입 → 빌드 → 도달한 묶음 실행(기록 남김) → 테스트 결과 기록 + 판정기 판정(전체 판정, O2·O4·O5·O6를 하나씩 뺀 판정).
3. **순서:** A 먼저, 그다음 B1·B2를 고정 seed(`20261119`)로 섞은 순서. 시간 안에 다 못 돌리면 **섞은 순서의 앞부분까지** 보고한다. 골라서 돌리지 않으므로 앞부분은 무작위 표본이다.
4. **제외:** 패치 적용 실패, 하네스 삽입 실패, 빌드 실패. 이번에는 빌드 실패 8개.
5. **환경:** WSL Ubuntu 22.04, 메모리 7.7GB, 작업 공간 4개 동시 실행. 변이 하나에 평균 약 7.5분(한 줄 실행 기준).

이 규칙들은 변이를 실행하기 **전에** 커밋했다. 실행 중에 바꾼 실행 방식은 7절에 모두 적었다.

**표본 구성:** 앞 100개의 묶음 비율(A 8, B1 71, B2 21)은 전체 244개의 비율(A 8, B1 181, B2 55)과 거의 같다. 전체 탐지율은 대표성이 있다. 다만 SWAP·LOCK·ERR처럼 원래 개수가 적은 종류는 표본이 1~5개뿐이라 종류별 숫자는 참고용이다.

| O6 (커밋) | 9/12 | 3 |
| O4 (잔고 변경) | 11/12 | 1 |

precompile에 들어갈 때·나올 때를 보는 O2가 탐지의 중심이다. 거래 전후만 보는 A1이 0개였던 것과 같은 이야기다. **버그는 거래 중간, precompile 경계에서만 보인다.**

## 6. 사례

### 6.1 판정기만 잡은 변이 (기존 테스트는 모두 통과)

**A01: GHSA-mjfq 보안 수정 되돌리기**
- **바꾼 것:** `runNativeAction`에서 `AddPrecompileFn(snapshot)`(되돌릴 시점 기록)을 precompile 실행 **전**에서 **성공한 뒤**로 옮겼다. precompile이 Cosmos 쪽 상태를 일부 바꾸다 실패하면 되돌릴 기록이 없어서, EVM 쪽만 되돌려지고 Cosmos 쪽 변경은 남는다.
- **판정기가 본 것:**
  - distribution: 되돌린 호출이 남긴 bank 잔고(1.0041…)가 그대로 커밋됨. 되돌리기 전 값은 1.0207…이어야 했다(R1-S).
  - staking: 되돌린 호출의 `coin_spent`·`coin_received`·`delegate` 이벤트가 최종 이벤트에 4번씩 남음(R1-E).
  - 총 5묶음에서 위반 67건.
- **기존 테스트:** 8묶음 모두 PASS. 실패해야 할 호출이 에러를 냈는지만 보고, 그 뒤 Cosmos 쪽 상태가 원래대로 돌아왔는지는 확인하지 않는다.
- **주의:** 규칙 설계에 쓴 버그 계열이므로 **성능 근거로 세지 않는다.** 이 사례가 보여 주는 것은 "업스트림 정상 테스트는 이 실제 취약점이 다시 들어와도 통과한다"는 점이다.

**C028: 컨트랙트가 호출할 때만 `FlushToCacheCtx` 오류 무시 (B2, 자동 생성)**
- **바꾼 것:** precompile 실행 전에 EVM 쪽 최신 잔고를 Cosmos 쪽 캐시에 옮겨 적는 단계(`FlushToCacheCtx`)가 실패해도, 호출자가 컨트랙트이면 멈추지 않고 진행한다.
- **판정기가 본 것 (staking, R2-W):** precompile에 들어가는 순간 같은 계정의 StateDB 잔고는 1.999… ETH, bank 잔고는 1 ETH. 옮겨 적기가 안 된 채로 precompile이 실행됐다.
- **기존 테스트:** 8묶음 모두 PASS.
- **재확인:** 같은 부하에서 다시 돌려도 위반이 똑같이 나왔고, 깨끗한 버전은 두 번 모두 위반 0이었다(6.4절). 판정기가 잘못 울린 것이 아니다.
- **의미:** 판정기 설계와 상관없이 자동으로 만든 변이다. 특정 문맥(컨트랙트 호출)에서만 드러나는 버그를 판정기만 잡은 사례다. 다만 **사례 1개**이므로 "이런 경우도 잡는다"는 예시이지 성능 증명은 아니다.

### 6.2 둘 다 잡은 변이 (10개)
- 잔고 계산 바꾸기: M202·M212(`SWAP`), M213(`DEL`), M246(`DEL`), M012(`LOCK`) → R2-W
- 중첩 호출에서만 되돌림 처리 빼기: C116·C153(`B2 DEL`, `NEST`) → R1-E·R1-S
- M103·M095(statedb 조건 끄기), M284(staking 오류 무시 → R3-D)

### 6.3 기존 테스트만 잡은 변이 (25개)
대표 사례와 판정기가 놓친 이유:

| 변이 | 기존 테스트가 잡은 방법 | 판정기가 놓친 이유 |
|---|---|---|
| A04 (#1187 되돌림: 잠긴 잔고를 커밋 때 다시 읽음) | 베스팅 계정 위임 테스트가 "bank 잔고가 위임액+gas보다 많이 줄었다"로 실패 (2.000… 대 1.000… ETH) | 잔고가 실제로 틀어졌는데 R2-W가 울리지 않았다. **판정기 개선 후보** |
| A05 (모듈·차단 계정 검사를 잔고가 늘 때만) | "모듈 계정으로 보내는 호출은 VM 오류가 나야 한다" 테스트가 실패 | 보내면 안 되는 곳으로 보냈을 뿐, 장부는 서로 맞는다. 판정기 범위 밖 |
| M283·M288·M293·M315 (staking·distribution 입력 검사 끄기) | "에러가 나야 하는데 안 남" | 입력 검사 누락은 상태 불일치가 아니다. 판정기 범위 밖 |
| M154·M158 (`StateDB.Commit`의 precompile 캐시 기록 경로 끄기·지우기) | distribution은 메모리 폭주로 끝나지 않음(`MEMOUT`), erc20·gov·staking 등은 `FAIL` | precompile 변경이 커밋되지 않는데 커밋 시점 검사(O6)가 울리지 않았다. 원인은 아직 분석하지 않았다. **판정기 개선 후보** |

기존 테스트만 잡은 25개 중 예상 규칙이 R2-W인 것이 11개다. 테스트가 잔고 이상으로 잡았다면 판정기도 원래 잡았어야 한다. 하나씩 원인을 보는 일이 판정기의 다음 개선 과제다.

### 6.4 재확인: 부하 때문에 나온 결과가 아닌지

작업 공간 4개가 동시에 도는 같은 부하에서 staking 묶음을 따로 다시 돌렸다(`recheck.sh`, 결과 `results/recheck/`).

| 대상 | 테스트 | 판정기 | 결론 |
|---|---|---|---|
| 깨끗한 버전 | 92 통과 / 0 실패 | 위반 0 | 부하 때문에 테스트가 실패하거나 판정기가 잘못 울리지 않는다 |
| C028 | 92 통과 / 0 실패 | **R2-W 1건 (재현)** | 판정기 탐지가 진짜다 |
| A04 | 91 통과 / **1 실패** | 위반 0 | 테스트 탐지가 진짜다 |
| A05 | 57 통과 / **1 실패** | 위반 0 | 테스트 탐지가 진짜다 |

### 6.5 아무도 못 잡은 변이 (62개)
- **R2-A 산술 검사 14개:** 정상 테스트는 넘침·모자람이 일어날 만큼 큰 값이나 0 근처 값을 쓰지 않는다.
- **B2 조건부 18개:** 줄은 실행되지만 문맥 조건(중첩 2회 이상, 베스팅, 낮은 gas 등)이 성립하지 않았을 수 있다.
- **동작이 원본과 같은 변이(등가 변이):** 따로 걸러 내지 않았다. 그래서 위 탐지율은 모두 보수적인 값이다.

이 몫은 판정기가 아니라 **입력**의 문제다. 버그를 실제로 터뜨리는 입력 생성기가 채울 부분이다.

## 8. 해석: 이 결과로 말할 수 있는 것과 없는 것

| 주장 | 근거 | 강도 |
|---|---|---|
| 기존 정상 테스트는 실제 취약점 계열(mjfq)을 못 막는다 | A01: 8묶음 모두 통과, 판정기는 5묶음 67건 | 강함 |
| 거래 전후 비교로는 이런 버그가 안 보인다 | A1 0/97 | 강함 |
| precompile 경계 관찰(O2)이 탐지의 핵심이다 | O2를 빼면 12개 중 8개를 놓침 | 중간 |
| 판정기는 테스트가 놓친 문맥 의존 버그를 잡을 수 있다 | C028 (재현 확인) | 약함 (사례 1개) |
| 되돌림 계열(R1)에서는 판정기가 테스트보다 낫다 | 3/10 대 2/10 | 약함 (표본 작음) |
| 판정기가 전반적으로 기존 테스트보다 잘 잡는다 | 12% 대 36% | **주장할 수 없음** |

**정리:** 정상 테스트를 입력으로 하면 판정기 단독 탐지율은 기존 테스트보다 낮다. 판정기는 테스트를 대체하는 도구가 아니라, 테스트가 확인하지 않는 **precompile 경계의 상태 일관성**을 보완하는 도구다. 다음 과제는 두 가지다.
1. 잔고 일관성(R2-W) 쪽에서 테스트만 잡은 11개의 원인을 분석해 판정기를 보강한다.
2. 버그를 실제로 터뜨리는 입력 생성기를 만든다.

## 9. 한계

- **중간 결과다.** 97개, 신뢰 구간이 넓다. 실행은 계속되며 최종 숫자는 바뀔 수 있다.
- **입력이 정상 테스트뿐이다.** 판정기는 버그가 실행 중에 드러나야만 잡을 수 있다.
- **등가 변이를 걸러 내지 않았다.** 탐지율은 보수적인 값이다.
- **기존 테스트와 판정기가 아는 정보가 다르다.** 테스트는 시나리오별 정답을 알고, 판정기는 일반 규칙만 안다. 두 숫자는 "같은 조건에서 누가 더 많이 잡나"이지, "같은 능력"의 비교가 아니다.
- **A 묶음은 설계에 쓴 버그 계열을 포함한다.** 그래서 따로 집계했다.
