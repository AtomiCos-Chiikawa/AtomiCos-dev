# 오탐 사전 측정: 업스트림 정상 테스트 스위트 (7단계 추가, 11단계 예비)

판정 규칙은 세 사례를 보고 설계했다. 그래서 "세 사례의 수정 버전에서 위반 0건"은 근거가 약하다. 여기서는 설계에 쓰지 않은 cosmos/evm의 precompile 통합 테스트 스위트를 하네스와 판정기에 통과시킨다. 대상은 v0.7.x 계열의 최신 패치 릴리스 v0.7.4(`ba66d31`)다. 여기서 나오는 위반은 오탐이거나 실제 문제다. 어느 쪽이든 설명해야 한다.

```bash
./eval/fp-upstream/run.sh       # 두 세트 모두
```

```bash
./eval/fp-upstream/run.sh B     # set B만
```

| set | 스위트 | 성격 |
|---|---|---|
| A | staking, distribution | R3 판정식을 고치는 데 사용했다. 고친 뒤의 0건은 독립 근거가 아니다 |
| B | bank, erc20, werc20, gov, slashing, ics20 | 규칙 설계와 수정에 한 번도 보지 않았다 |

## 결과 (2026-11-19)

| set | 스펙 | precompile 호출 | 되돌림 | 위반 |
|---|---|---|---|---|
| A | 169 (모두 통과) | 2,216 | 4,233 | 처음 판정 R3 106건, R3 수정 후 0건 ([summary-A.txt](results/summary-A.txt)) |
| B | 289 (모두 통과, erc20 스위트 자체가 8개를 건너뜀) | 1,283 | 10,973 | 0건 ([summary-B.txt](results/summary-B.txt)) |

set A의 R3 106건은 판정식이 틀려서 나왔다(cosmos/evm 버그 아님). 위임액이 바뀌기 전에 x/distribution 훅이 쌓인 보상을 자동으로 인출하는데 R3-D/U가 이를 빼먹었다. 위반 하나하나의 차이가 자동 인출 보상과 정확히 같았다. `docs/rules.md` R3을 고친 뒤 같은 기록을 다시 판정해 0건을 확인했다.

## 한계
- 버전 하나(v0.7.4)만 쟀다. v0.5와 v0.1 계열의 정상 스위트에서는 아직 재지 않았다.
- 업스트림 테스트는 정상 동작과 실패 동작을 둘 다 검사하지만 공격형 입력은 거의 없다. 오탐 측정으로는 쓸 만하고 미탐 측정으로는 쓸 수 없다.
- 기록 파일(`*.trace.jsonl.gz`, 수 MB)은 git에서 제외했다. `run.sh`로 다시 만든다.
- `results/coverage.md`는 `./eval/fp-upstream/coverage.sh`가 판정기 출력의 통계(`stats`)에서 만든다. 기록 파일 없이 커밋된 `*.check.txt`만으로 다시 만들 수 있다.
- 기록 수, 되돌림 수, precompile 호출 수는 실행마다 조금씩 달라진다. 예를 들어 bank 기록 수는 첫 측정(Linux)에서 3,226개, 2026-11-19 macOS에서 다시 돌렸을 때 3,228개, 3,229개였다. 스펙 289개 통과와 위반 0건은 매번 같았다.
- `results/summary-A.txt`는 이제 `run.sh`가 만든 출력이다. R3 106건이 나온 첫 판정은 출력 파일이 남아 있지 않고, 그 내용을 손으로 정리한 메모가 첫 커밋의 `summary-A.txt`에 남아 있다.
- 결과 파일은 하네스 수정(관찰 읽기 격리, 2026-11-19) 뒤에 다시 만든 것이다. 수정 전 하네스는 v0.7에서 보상 조회의 쓰기를 실행 중인 저장소에 남겨, 커밋되지 않는 gas 추정 실행에서 `delegate` 호출 수를 늘렸다(staking: 수정 전 684회, 수정 후 672회). 위반 수는 수정 전후 모두 0건이다.
