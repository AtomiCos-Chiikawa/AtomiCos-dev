# 오탐 사전 측정: 업스트림 정상 테스트 스위트 (7단계 추가, 11단계 예비)

판정 규칙은 세 사례를 보고 설계했다. 그래서 "세 사례의 수정 버전에서 위반 0건"은 근거가 약하다. 여기서는 설계에 쓰지 않은 cosmos/evm의 precompile 통합 테스트 스위트를 하네스와 판정기에 통과시킨다. 대상은 v0.7.x 계열의 최신 패치 릴리스 v0.7.4(`ba66d31`)다. 여기서 나오는 위반은 오탐이거나 실제 문제다. 어느 쪽이든 설명해야 한다.

```bash
./eval/fp-upstream/run.sh       # 두 세트 모두
```

```bash
./eval/fp-upstream/run.sh B     # set B만
```

| set | 스위트 | 성격 |
|---|---|---|
| A | staking, distribution | R3 판정식을 고치는 데 사용했다. 고친 뒤의 0건은 독립 근거가 아니다 |
| B | bank, erc20, werc20, gov, slashing, ics20 | 규칙 설계와 수정에 한 번도 보지 않았다 |

## 결과 (2026-11-19)

| set | 스펙 | precompile 호출 | 되돌림 | 위반 |
|---|---|---|---|---|
| A | 169 (모두 통과) | 2,216 | 4,233 | 처음 판정 R3 106건, R3 수정 후 0건 ([summary-A.txt](results/summary-A.txt)) |
| B | 289 (모두 통과, erc20 스위트 자체가 8개를 건너뜀) | 1,283 | 10,973 | 0건 ([summary-B.txt](results/summary-B.txt)) |

set A의 R3 106건은 판정식이 틀려서 나왔다(cosmos/evm 버그 아님). 위임액이 바뀌기 전에 x/distribution 훅이 쌓인 보상을 자동으로 인출하는데 R3-D/U가 이를 빼먹었다. 위반 하나하나의 차이가 자동 인출 보상과 정확히 같았다. `docs/rules.md` R3을 고친 뒤 같은 기록을 다시 판정해 0건을 확인했다.

## 다른 버전 (2026-11-19)

같은 스위트를 다른 릴리스 계열에도 돌렸다(`FP_VERSION=<버전> ./eval/fp-upstream/run.sh`, 결과는 `results/<버전>/`). 모든 스위트의 테스트가 통과했고 판정 불가는 없었다.

| 버전 | 커밋 | 하네스 | 스위트 | 스펙 (통과/실패) | 판정기 결과 |
|---|---|---|---|---|---|
| v0.7.4 | `ba66d31` | v07 | 8 | 458 / 0 | 0건 |
| v0.6.5 | `e04dc04` | v07 | 8 | 458 / 0 | 0건 |
| v0.5.1 | `e2f6e47` | v05 | 8 | 454 / 0 | R1-E 19건 (staking 11, erc20 6, ics20 2) |
| v0.2.0 | `0fff8c1` | v01 | 6 (slashing·ics20 스위트 없음) | 388 / 0 | R1-E 15건 (staking), A1 11건 |

v0.1.x 계열에는 태그가 v0.1.0 하나뿐이다. 이 태그는 GHSA-mjfq 수정 전이고 디렉터리 구조(`example_chain/`)도 달라서, 그 계열의 수정 커밋인 v0.2.0을 대신 썼다.

위반은 하나씩 trace로 확인했다.
- **v0.5.1 staking R1-E 11건은 실제 결함이다.** 되돌릴 때 precompile 저장소는 되돌리지만 precompile 캐시(`cacheCtx`)에 쌓인 이벤트는 되돌리지 않는다. 그래서 되돌린 위임 호출의 이벤트가 다음 호출로 넘어가 커밋에 남는다. 예를 들어 `db716`은 위임 호출이 모두 되돌려졌는데도 커밋(seq 3796)에 delegate 이벤트가 있다. 상태 변경은 없고 이벤트만 틀린다. GHSA-8pfh 수정(`79089fe`, v0.5.1에 포함)은 메인 컨텍스트의 이벤트만 복원한다. 캐시 쪽은 v0.6.0의 `x/vm/statedb/journal.go`(`OverrideEvents(pc.prevEvents)`)에서 고쳐졌고 변경 기록에는 없다. v0.6.5가 0건인 것과 맞는다. 기존 테스트는 이 결함이 있는 v0.5.1에서 모두 통과했다.
- **v0.2.0 staking R1-E 15건도 같은 결함이다.** v0.2.0은 8pfh 수정 전이기도 하다.
- **v0.2.0 staking A1 11건은 실제 결함이다.** 컨트랙트 위임자의 보상이 자동 인출된 뒤 사라진다. 보상, distribution 모듈 잔고, 총발행량이 같은 금액만큼 줄고 그 금액을 받은 계정이 없다. 커밋 때 bank 잔고를 보상 인출을 모르는 EVM 쪽 잔고로 덮어쓰기 때문이다. v0.3.0의 `BalanceHandler`(cosmos/evm #201)가 이 문제를 다룬다. v01 계열에는 O2가 없어서 R2-W와 R3는 판정하지 못했고 보조 검사 A1만 잡았다.
- **v0.5.1 erc20 6건과 ics20 2건은 오탐이다.** R1-E는 이벤트를 내용(종류와 속성)만으로 구별한다. 그래서 되돌린 호출과 내용이 같은 정상 이벤트가 커밋에 있으면 남은 이벤트로 센다. erc20은 같은 전송을 두 번 해서 두 번째만 되돌린 경우이고, ics20은 되돌린 전송과 커밋 때 잔고 되쓰기가 같은 `coin_spent`를 낸 경우다. 같은 이유로 실제 결함 사례에서도 개수가 실제보다 많게 나온다(`db879`: 5회로 보고, 실제로 남은 것은 3회). 규칙은 고치지 않았다(11단계 전 개선 과제).

정리하면 버전 4개, 스펙 1,758개에서 판정기 위반 34건이 나왔다. 이 중 26건은 테스트가 모두 통과한 버전에 실제로 있던 결함이고 8건은 R1-E의 오탐이다. 이와 별도로 보조 검사 A1 11건도 실제 결함(보상 소실)이다. v0.5.1에서는 R1이 처음으로 제대로 검사됐다. 되돌림 1,119회(staking 577, distribution 542)에서 후보가 생겼고, 커밋에 남지 않은 후보는 위반으로 세지 않았다.

## 한계
- 버전 하나(v0.7.4)만 쟀다. v0.5와 v0.1 계열의 정상 스위트에서는 아직 재지 않았다.
- 업스트림 테스트는 정상 동작과 실패 동작을 둘 다 검사하지만 공격형 입력은 거의 없다. 오탐 측정으로는 쓸 만하고 미탐 측정으로는 쓸 수 없다.
- 기록 파일(`*.trace.jsonl.gz`, 수 MB)은 git에서 제외했다. `run.sh`로 다시 만든다.
- `results/coverage.md`는 `./eval/fp-upstream/coverage.sh`가 판정기 출력의 통계(`stats`)에서 만든다. 기록 파일 없이 커밋된 `*.check.txt`만으로 다시 만들 수 있다.
- 기록 수, 되돌림 수, precompile 호출 수는 실행마다 조금씩 달라진다. 예를 들어 bank 기록 수는 첫 측정(Linux)에서 3,226개, 2026-11-19 macOS에서 다시 돌렸을 때 3,228개, 3,229개였다. 스펙 289개 통과와 위반 0건은 매번 같았다.
- `results/summary-A.txt`는 이제 `run.sh`가 만든 출력이다. R3 106건이 나온 첫 판정은 출력 파일이 남아 있지 않고, 그 내용을 손으로 정리한 메모가 첫 커밋의 `summary-A.txt`에 남아 있다.
- 결과 파일은 하네스 수정(관찰 읽기 격리, 2026-11-19) 뒤에 다시 만든 것이다. 수정 전 하네스는 v0.7에서 보상 조회의 쓰기를 실행 중인 저장소에 남겨, 커밋되지 않는 gas 추정 실행에서 `delegate` 호출 수를 늘렸다(staking: 수정 전 684회, 수정 후 672회). 위반 수는 수정 전후 모두 0건이다.
